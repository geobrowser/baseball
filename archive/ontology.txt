Baseball Ontology for Geo Knowledge Graph
==========================================

Maps MLB Stats API live data (primary) + Retrosheet historical data (backfill)
to GRC-20 entities.

Data source priority:
  - MLB Stats API is the primary source — live, current-season, and Statcast data.
  - Retrosheet backfills historical depth — pre-2015 play-by-play, game-level stats
    going back to 1871, Negro League data, and curated collections (no-hitters, etc.).
  - Where both sources cover the same entity (e.g., a 2024 game), MLB API is preferred
    for richer fields (Statcast, weather strings, venue coordinates) and Retrosheet
    supplements with fields MLB API lacks (Retrosheet game IDs, umpire crews, manager IDs).
  - Cross-referencing uses the Chadwick Bureau register for player ID mapping
    (MLB integer IDs ↔ Retrosheet string IDs).

Conventions:
  - "Name", "Types", and "Description" are system properties (already exist in root space).
  - All Type schemas implicitly include Name, Types, Description — listed below only when
    additional properties are defined.
  - "Relation" data type means the property points to another entity (via a Types-style relation).
  - Reusable properties (used by multiple types) are defined once and shared.
  - Prefer relations to reusable entities over text values. Text is only used for
    truly free-form data (descriptions, event codes, wind strings) or per-entity
    identifiers (Retrosheet ID, nicknames).
  - Each property notes its source: [MLB], [RS], or [Both] where it matters.

  For Retrosheet plays without natural-language descriptions, construct from event code and game state.

Reference entities:   Created from both sources. Deduplicate by name.

================================================================================
TEXT vs RELATION DECISION LOG
================================================================================

Properties kept as Text (free-form, not suitable for entity-ification):
  - Retrosheet ID / Retrosheet Game ID — unique per-entity identifiers, not reusable
  - Nickname — team-specific text (e.g., "Yankees"), not a shared concept
  - Play description — stored in system Description property, free-form natural language
  - Wind — free-form string (e.g., "6 mph, In From CF"), infinite variations
  - Ejection Reason — free-form string, unique per incident

Properties converted to Relations (finite reusable sets):
  - City, State, Country — geographic entities shared across Person, Team, Ballpark
  - League — finite set of ~20, shared across Team and historical contexts
  - Position — 11 positions, shared across Roster Entry and Fielding Performance
  - Game Type — 8 types, shared across all games
  - Role — 4 roles, shared across Person and Ejection
  - Handedness — 3 values (L/R/S), shared across Bats and Throws on Person
  - Pitch Type — ~15 types, shared across all Pitch entities
  - Pitch Call — ~12 outcomes, shared across all Pitch entities
  - Play Event — ~30 outcomes, shared across all Play entities
  - Hit Trajectory — 4 categories, shared across Pitch entities
  - Sky Condition — ~7 values, shared across Game entities
  - Day/Night — modeled as boolean (Day Game: true/false) since it's binary
  - Surface Type — 2 values, shared across Ballpark entities
  - Roof Type — 3 values, shared across Ballpark entities
