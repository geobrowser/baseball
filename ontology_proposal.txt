================================================================================
RETROSHEET x GEO — ONTOLOGY PROPOSAL (DRAFT v0.1)
================================================================================

Goal: model the 14 parsed Retrosheet datasets as a Geo knowledge graph using
GRC-20 conventions. Top-level types are browseable nodes; reference types are
small finite sets pointed to by relations; relation-entity types carry
per-context data (rosters, stat lines).

Conventions used:
  - Finite/categorical fields → relations to reference entities (not text)
  - Reusable named-place fields (city / state / country / league) → relations
    to first-class entities (not text), so each city, state, country, and
    league has its own browseable page
  - **Name is a first-class system property — use it for the entity's full
    common name. Avoid auxiliary name fields like First name, Last name,
    Full legal name, Nickname, Full name. When alternate identities matter
    (birth name, AKA), use a single "Also known as" multi-text property.**
  - **Year vs Date convention:** when the source provides only a year
    (e.g., teams.first_year), use Integer with property names ending in
    "year". When the source provides a full date (e.g., ballparks.start_date),
    use Date with property names ending in "date". Don't fake Jan-1 Date
    values from year-only data.
  - Booleans only when truly binary and unlikely to gain values
  - Numeric stats → Integer / Float64
  - Cross-entity references → Relation properties
  - One Person entity per individual; their role(s) are a multi-relation
  - Stat lines (batting/pitching/fielding) modeled as entities with relations
    to Game + Person + Team, since they are themselves browseable units of
    performance and may be linked from blocks/queries
  - **Position breakdowns on season-summary entities (Roster entry, stints)
    are modeled as ordered multi-relations to Position with per-position
    Games played stored on the relation entity — not as a wide row of
    "Games at first base / Games at shortstop / …" properties.**


================================================================================
NAMING CONVENTIONS
================================================================================

All type, property, and reference-instance names follow these rules:

  1. Only the first letter of the first word is capitalized, unless the
     word is an acronym (RBI, ERA, MLB, ID, OPS, WHIP, DH, PBP, ISO,
     DNP, etc.).
  2. Minor words (prepositions, articles) stay lowercase in the middle
     of a name: "Runner on 1B", "Top of inning", "Hit by pitch",
     "Reached on error", "Grounded into double play".
  3. Parenthetical units are not capitalized: "Height (inches)",
     "Weight (lbs)", "Duration (minutes)", "Innings pitched (outs)".
  4. Boolean properties:
     - Use positive phrasing without an "Is" prefix for official stats:
       Day game, Game started, Complete game, Save, Loss, No outs
       recorded, Started at position, Used DH.
     - Use an "Is" prefix for state descriptions: Is plate appearance,
       Is at bat, Is designated hitter, Is scoring play.

SECTION A — TOP-LEVEL ENTITY TYPES
================================================================================

These are primary browseable nodes that users land on, search for, link to.


-- Types --

Name: Person
Types: Type
Description: A person in baseball history — player, manager, coach, or umpire.
A single Person may hold multiple roles across their career.
Properties:
  Name, Description, Cover, Avatar,
  Also known as,
  Birth date, Birth place,
  Death date, Death place,
  Bats, Throws, Height (inches), Weight (lbs),
  Hall of fame,
  Retrosheet person ID

Note: Roles is NOT stored on Person — it's inferable from Roster entries
(player) and Staff stints (manager / coach / umpire / official scorer).

Note: Birth place / Death place are single multi-target relations to
the most specific known place — City, State or region, or Country.
The City entity itself relates to State or region and Country, so the
hierarchy is walkable from any starting level. This handles records
where Retrosheet provides only state or only country (with no city).
Population rule: link to City when birth_city is present; otherwise to
State or region; otherwise to Country.

Note: Per-role debut/last-game dates (player / coach / manager / umpire)
are not properties on Person. They are captured by Roster entry (player)
and Staff stint (coach / manager / umpire) entities, which carry the
first-game and last-game dates for each season-team-role combination.

Source: players.json
Name format: common full name (e.g., "Shohei Ohtani", "Aaron James Judge")
  — sourced from players.full_name, falling back to "{first_name} {last_name}".
Also known as: multi-text — populate from players.birth_name and
  players.alt_name when they differ from Name.
Description: e.g., "Two-way player. Bats L / Throws R. Active 2018–present."


-- Types --

Name: Team
Types: Type
Description: A baseball franchise across its history. One entity per franchise
(not per season — season membership is captured by Roster entries and Game
participation).
Properties:
  Name, Description, Cover, Avatar,
  Also known as,
  City, Leagues,
  First active year, Last active year,
  Home ballparks,
  Retrosheet team ID, Alternate Retrosheet IDs

Note: City is a relation → City entity (which itself relates to State or
region and Country). Leagues is a multi-relation → League entity, since
some franchises played in multiple leagues over their history (Houston
Astros: NL → AL in 2013; many Negro League teams switched circuits as
leagues folded and reformed). Nickname and "full name" are not separate
properties — Name holds the full team name.

Note: 77 of 293 teams in Retrosheet's teams.json have an empty league
field (mostly very old or disbanded teams). Skip the Leagues relation
entirely for those rather than relating to a placeholder.

Note: Home ballparks is a multi-relation → Ballpark, with relation entity
type **Team ballpark tenancy** (defined in Section A2) carrying first
and last game dates the team played at that park. Order: chronological
by First date.

Source: teams.json
Name format: full team name "{city} {nickname}" (e.g., "New York Yankees")
Also known as: any historical alternate names from teams.json
Description: league + active years (e.g., "AL franchise, 1903–present")

-- Types --

Name: Game
Types: Type
Description: A single baseball game between two teams.
Properties:
  Name, Description, Cover,
  Date, Game number, Day of week,
  Teams,
  Venue, Attendance, Duration (minutes),
  Day game, Game length (outs), Innings played, Used DH,

Name format: "AWAY @ HOME — YYYY-MM-DD" (e.g., "NYA @ LAN — 2024-10-30")
Description: final score + key pitchers


-- Types --

Name: Season
Types: Type
Description: A single MLB (or affiliated league) season.
Properties:
  Name, Description, Cover,
  Year, League,
  Start date, End date

Source: derived from gamelogs / schedules
Name format: "{Year} {League}" (e.g., "2024 MLB", "1925 NNL")
Description: high-level season summary


-- Types --

Name: Roster entry
Types: Type
Description: A person's affiliation with a team for a single season, with
their primary listed position. (One per player–team–season; a mid-season
trade produces multiple entries.)
Properties:
  Name, Description,
  Person, Team, Season,
  Games played (total),
  Positions played,
  First game of season (date), Last game of season (date),
  Season batting average, Season on-base percentage,
  Season slugging, Season OPS,
  Season ERA, Season WHIP,
  Season fielding percentage

Note: Season aggregate stats are Float64 derived properties computed at
publish time by aggregating Batting line / Pitching line / Fielding line
records for this player-team-season. All are null when not applicable
(e.g., Season ERA is null for a player who never pitched). Per-game
ERA / AVG / FP are NOT stored on stat lines because they're noisy at
single-game granularity (1 IP with 1 ER = 9.00 ERA tells you nothing).

Note: Per-position game counts are not stored as a wide row of "Games at
X" properties. Instead, "Positions played" is an ordered multi-relation
to Position entities, with relation entity type **Roster position
assignment** (defined in Section A2). Each relation entity carries a
"Games played" property holding the count for that position. The
first relation in the order is the primary position (from rosters.json);
subsequent relations are ordered by descending Games played.

Source: rosters.json + allplayers.ndjson (joined on player+team+season)
Name format: "{Person Name} — {Team} {Year}"
Description: "DH, 135 G, 2024" style summary


-- Types --

Name: Staff stint
Types: Type
Description: A manager / coach / umpire affiliation for a single season.
Mirrors Roster entry but for non-player roles. (One per person–team–season
for managers and coaches; umpire stints are league-wide so Team is null.)
Properties:
  Name, Description,
  Person, Role, Team, Season,
  Games (total),
  First game of season (date), Last game of season (date)

Note: Role is a relation → Person role (Manager / Coach / Umpire / Official
scorer). Team is omitted for umpire stints since umpires are not affiliated
with a single team. We use one unified type instead of separate
Manager stint / Coach stint / Umpire stint types because the schema is
identical and Role disambiguates.

Source: derived from gamelogs (h_manager_id, v_manager_id, hp_umpire_id),
gameinfo (umphome, ump1b/2b/3b, umplf/rf, oscorer), and players
debut/last_* dates.
Name format: "{Person Name} — {Team or '—'} {Year} ({Role})"
Description: e.g., "112 games, 2024 (Manager)"

-- Types --

Name: Play
Types: Type
Description: A single plate appearance / play-by-play event with full game
state at the moment of the event.
Properties:
  Name, Description,
  Game, Inning, Half inning, Plate appearance number,
  Batting team, Pitching team,
  Score (visiting), Score (home),
  Batter, Pitcher, Lineup position,
  Batter handedness, Pitcher handedness,
  Event code,
  Event types, Fielders involved, Hit trajectory,
  Is plate appearance, Is at bat, Ball in play,
  Balls, Strikes,
  Outs before, Outs after,
  Runner on first after, Runner on second after, Runner on third after,
  Pitcher responsible for runner on first,
  PBP source

Note: Date, Venue, and Game type are not stored on Play — reachable
via the Game relation. Score (visiting) and Score (home) ARE kept
because they are mid-game scores at the time of the play, distinct
from the Game's final scores.

Note: Outcome and trajectory are decomposed into three orthogonal
relations rather than a wall of "Was single / Was double / Was fly ball"
booleans:
  - **Event types** (multi → Play event type) — atomic outcomes. A
    plain single is ["Single"]; a strikeout-wild-pitch is
    ["Strikeout", "Wild pitch"]; a 6-4-3 GIDP is
    ["Groundout", "Double play"].
  - **Fielders involved** (multi-relation, ordered → Position) — the
    fielder positions that touched the ball, in sequence. For "63"
    (groundout SS to 1B): [Shortstop, First base]. For "8/F" (fly to
    CF): [Center field]. For "S7" (single to LF): [Left field].
    Reuses the existing Position type since positions 1–9 already
    encode the field areas.
  - **Hit trajectory** (relation → Hit trajectory) — Fly ball, Ground
    ball, Line drive, Pop up, Bunt variants, etc.

The raw Retrosheet "Event code" text is preserved as-is for fidelity
and round-trip parsing.

Source: plays.ndjson
Name format: "{Game} — {Inning}{T/B} #{PA}" (e.g., "NYA @ LAN 2024-10-30 — 8T #42")
Description: short event summary

Name: Scheduled game
Types: Type
Description: A scheduled (not necessarily played) game, including future

================================================================================
SECTION A2 — RELATION ENTITY TYPES
================================================================================

Relation entity types are the *type* of an entity that *acts as* the link
between two other entities. A relation property has both a "to" target
type and a "relation entity" type; the relation entity type defines the
schema of properties stored on the relation itself.

Each relation entity type below is itself an entity with Types: Type and
its own Properties relations. Treated as first-class schemas, not
ad-hoc property bags.


-- Types --

Name: Team game record
Types: Type
Description: The relation entity for a Game → Team link. One per
team-per-game (so two per Game: one Home, one Away). Carries everything
that is "this team in this specific game."
Properties:
  Side,
  Score, Result, Manager, Starting pitcher,
  At bats, Hits, Doubles, Triples, Home runs,
  Runs batted in, Walks, Strikeouts, Stolen bases, Left on base

Source: gamelogs.ndjson v_* and h_* fields, plus gameinfo manager IDs
Used on: Game.Teams relation


-- Types --

Name: Umpire assignment
Types: Type
Description: The relation entity for a Game → Person umpire link.
One per umpire per game. Carries the umpire's position for that game.
Properties:
  Umpire position

Source: gameinfo.ndjson umphome / ump1b / ump2b / ump3b / umplf / umprf
Used on: Game.Umpires relation
Ordering: relations are ordered home plate first, then 1B / 2B / 3B,
then LF / RF (postseason crews only).


-- Types --

Name: Roster position assignment
Types: Type
Description: The relation entity for a Roster entry → Position link.
One per position the player appeared at in that season-team. Carries
how many games the player played at that position.
Properties:
  Games played

Source: rosters.json (primary position) + allplayers.ndjson
(g_p / g_sp / g_rp / g_c / g_1b / … / g_pr counts)
Used on: Roster entry."Positions played" relation
Ordering: relations are ordered with the primary position first
(from rosters.json), then by descending Games played.


-- Types --

Name: Team ballpark tenancy
Types: Type
Description: The relation entity for a Team → Ballpark home-venue link.
One per (Team, Ballpark) combination. Carries the first and last date
the team played a home game at that park. Teams that share or change
parks (Yankees: Yankee Stadium I → temp digs → Yankee Stadium II;
A's split between Oakland and Sacramento) get multiple tenancy relations.
Properties:
  First game date, Last game date, Notes

Source: derived from gamelogs (filter to games where this team is
home, group by park_id, min/max date).
Used on: Team."Home ballparks" relation
Ordering: chronological by First game date.

SECTION D — KEY MODELING DECISIONS (FOR REVIEW)
================================================================================

1. **Person is one entity per individual, not per role.** A two-way player
   like Ohtani is one Person; their Roster entries carry the per-season
   position, and stat lines link back to them. Per-role activity is
   inferable from Roster entry / Staff stint membership — see decision 16.

2. **Roster entry is its own entity, not a relation-on-Team.** We chose
   this because (a) per-position game counts from allplayers.ndjson are
   rich enough to be browseable, and (b) a player traded mid-season has
   multiple entries and they each deserve their own page-style entity.
   Per-position games are modeled as an ordered "Positions played"
   multi-relation to Position with a Games played property on the
   relation entity (primary first, then descending by games played).
   Manager / coach / umpire stints follow the same shape via a unified
   Staff stint type with a Role relation.

3. **Stat lines (Batting / Pitching / Fielding) are entities.** They are
   joinable on (Person, Game) and represent the natural unit of
   single-game performance. Modeling them as entities lets us render
   data blocks like "Ohtani's batting lines this postseason" naturally.

4. **Play event codes are decomposed into orthogonal relations.**
   Rather than treating "S7/L" as one opaque text value or an inflated
   reference type with thousands of combinatorial instances, a Play
   relates to:
     - Event types (multi → Play event type) — atomic outcomes
     - Fielders involved (multi-ordered → Position) — fielder positions
       in sequence (positions 1–9 already encode the field areas)
     - Hit trajectory (single → Hit trajectory) — fly / ground / line /
       pop / bunt
   So "S7/L" becomes Event types=[Single], Fielders involved=[Left field],
   Hit trajectory=Line drive. "63/G" becomes Event types=[Groundout],
   Fielders involved=[Shortstop, First base], Hit trajectory=Ground ball.
   The raw Retrosheet event string is also preserved as Event code (Text)
   for round-trip fidelity. Decide later whether to materialize all
   6.5M plays or only postseason / notable subset.

5. **Game vs Scheduled game are separate types.** Scheduled games include
   future seasons (2026) and postponements; Games are played games with
   results. They share many properties but model different lifecycles.

6. **Notable game collections use Geo Blocks.** Each category is a
   Page-style entity whose Blocks include a Collection Data Block whose
   Collection items are Game entities. No new entity type for "membership."

7. **Day game stays as Boolean** (matching gamelogs.day_night = D/N).
   Sky condition / field condition / etc. are richer ref types.

8. **Locations are first-class entities.** City, State or region, and
   Country are top-level types. Birth/death places, team cities, and
   ballpark locations all relate to the same City / State / Country
   entities — so navigating to "Santo Domingo" surfaces every Person
   born there, every team based there, every ballpark located there.
   Cities relate to State or region and Country; State or region
   relates to Country. **Retrosheet does not provide lat/lon** —
   Ballpark.Location and City.Location require external geocoding and
   are optional/derived in Phase 1.

9. **Names follow the GRC-20 Name convention.** No First name, Last name,
    Full legal name, Nickname, or Full name properties. The full common
    name lives in Name; alternate identities (birth name, AKA) go in a
    single multi-text "Also known as" property where applicable.

10. **Years vs Dates.** Use Integer "year" properties when the source is
    year-only (Team.first_active_year, League.first_active_year). Use
    Date properties when the source carries full dates (Ballpark
    opening/closing, Person debut/last as captured on Roster entry /
    Staff stint, Game date). This prevents fake Jan-1 timestamps from
    polluting Date fields.

11. **Lineup state on Play is skipped.** The 27 lineup-state fields
    (l1..l9, lf1..lf9, f2..f9) are reconstructable from Batting lines +
    Fielding lines + substitution events. Storing 27 properties per
    play across 6.5M plays would balloon the graph for marginal value.
    If browseability of "who was on the field at this moment" matters
    later, add a thin "Lineup card" entity per (Game, Team, Inning).

12. **Pitching lines stay as one type.** Retrosheet stores one record
    per pitcher per game with a sequence number; "starter vs reliever"
    is captured by Pitching sequence + Game started boolean. No need
    for separate Starting pitcher line / Relief pitcher line types.

13. **Relation entity types are first-class types.** Whenever a relation
    carries data on the link itself, the relation entity has an
    explicitly defined type with its own Name, Types: Type, and
    Properties — the same shape as any other entity type. Section A2
    defines all such types in this ontology:
      - **Team game record** — relation entity for Game.Teams. Carries
        Side, Score, Result, Manager, Starting pitcher, and 10 team
        box totals (At bats / Hits / … / Left on base).
      - **Umpire assignment** — relation entity for Game.Umpires.
        Carries Umpire position.
      - **Roster position assignment** — relation entity for
        Roster entry.Positions played. Carries Games played.
    A relation property's schema is therefore "to" target type +
    "relation entity" type. Both are required when the relation
    carries data; only "to" is needed for a plain link.

14. **Birth / Death place collapse.** Person uses a single Birth place
    and single Death place relation, each with a multi-target type
    (City | State or region | Country). The most specific known place
    is linked; less granular records (state-only, country-only) link
    higher up the hierarchy. City entities relate to State or region
    and Country, so the chain is walkable from any starting point.
    Eliminates 4 redundant properties on Person.

15. **Don't denormalize values that are one hop away.** Across the
    ontology, a property is dropped when its value is reachable in one
    relation hop:
      - Year on Roster entry / Staff stint / Scheduled game
        (Season carries Year).
      - Date / Venue / Game type / Result on Batting line / Pitching
        line / Fielding line / Play (Game carries them; Result lives
        on Game.Teams[this team]).
      - Active years (text) on League (First/Last active year covers it).
      - Count on Play (just balls + strikes concatenated).
      - Bats / Throws on Roster entry (a Person attribute, not a
        season attribute).
    Exceptions (kept as deliberate denormalization):
      - Opponent team on stat lines — convenient single-property hop
        used in many queries.
      - Score (visiting) / Score (home) on Play — these are
        mid-game scores at the time of the play, distinct from the
        Game's final scores.
      - Day of week on Game / Scheduled game — derivable from Date,
        but cheap to store and used heavily by browsing UI.
      - Batter handedness / Pitcher handedness on Play — necessary
        because switch hitters' actual handedness varies per
        plate appearance based on pitcher.

16. **Roles is not stored on Person.** Person's roles (player /
    manager / coach / umpire / official scorer) are inferable from
    Roster entries and Staff stints. Storing them separately would
    require keeping a synced list. The Person role ref type stays —
    it's still used by Staff stint.Role.

17. **Team → Home ballparks is explicit.** Teams have a Home ballparks
    multi-relation → Ballpark with a Team ballpark tenancy relation
    entity carrying first/last game dates. Strictly derivable from
    gamelogs (group by team + park, min/max date), but published
    explicitly because (a) browseability — "what parks have the
    Yankees called home?" — and (b) tenancy windows are stable enough
    that a small materialized relation is much cheaper than scanning
    games every time.

18. **Negro Leagues are first-class.** League has instances for NNL, NAL,
    ECL, NSL etc. Teams and Persons from those leagues use the same model.

19. **Cardinality warning.** Plays (~6.5M), batting (~5.7M), pitching
    (~1.3M), fielding (~1.7M) are huge. Recommend phased publishing:
    Phase 1 = Persons, Teams, Ballparks, Seasons, Games + reference types.
    Phase 2 = Roster entries, postseason stat lines + plays.
    Phase 3 = full stat lines / plays history.

DATA-QUALITY NOTES (FROM TYPE VERIFICATION SWEEP)
================================================================================

Findings from running verify_types.ts / verify_types2.ts / verify_types3.ts
against data/parsed/ — issues to handle in the publish pipeline rather
than in the ontology:

  1. ballparks.json start_date / end_date is in mixed format:
     146 records ISO (YYYY-MM-DD), 115 records M/D/YYYY, 395 null.
     Normalize to ISO during parsing before publishing as Date.

  2. ejections.json has 2 records with role="NY1" — actual fields are
     shifted by one column (team is empty, umpire_id holds role letter,
     umpire_name holds umpire ID, inning holds umpire name, reason
     holds inning). Filter these during ingest.

  3. batting.gametype has 23 records with capitalized "Regular"
     (vs 5.65M "regular"). Lowercase during ingest.

  4. Roster position null occurs for ~4419 Negro Leagues records
     (1930s–40s). Skip the Roster position assignment relation
     for these rather than linking to a placeholder.

  5. teams.league is empty for 77 of 293 teams (mostly defunct early
     leagues). Skip Leagues relation rather than relating to a
     placeholder.

  6. schedules.time_of_day mapping for Day game Boolean:
       D, d, A   → true  (day, afternoon)
       N, n, E   → false (night, evening)
       0, null   → null  (postponed / unknown — skip property)

  7. Schedules / players debut dates use mixed YYYYMMDD vs YYYY-MM-DD
     formats across files. Normalize to ISO during parsing.

  8. plays.event has ~18,200 distinct codes in a 500k sample —
     confirming the decomposed Event types + Fielders involved + Hit
     trajectory model is correct. The full set is unbounded as
     combinations of position numbers and modifiers.
